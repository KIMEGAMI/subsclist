# SubscList 利用頻度向上・費用対効果分析 実装調査

最終更新: 2026-08-10

## 調査結果

| 項目 | 現状 |
| --- | --- |
| 基盤 | Next.js 16、TypeScript、Prisma 7、MySQL を利用しています。 |
| 認証 | 独自の署名付き `HttpOnly` セッション Cookie を使用し、メール認証済みユーザーをサーバー側で必須にしています。Google 認証も既存です。 |
| ユーザー・権限 | `User` に `plan`（FREE / PREMIUM / LIFETIME）があり、既存のプラン上限・Premium 制御があります。 |
| サブスク | `Subscription` に料金、請求周期、次回更新、カテゴリ、支払い方法、利用頻度、優先度、解約支援情報があります。論理削除も使用しています。 |
| 支払い・カテゴリ | `PaymentHistory`、`PaymentMethod`、`Category` を既存で利用しています。 |
| 通知 | 通知設定・送信履歴モデルと通知画面・送信APIが既存です。新しい通知機能はこれを拡張します。 |
| 画面 | ダッシュボード、サブスク一覧・詳細、分析、月次レポート、通知、CSV、解約支援、設定が既存です。共通枠は `AppShell` です。 |
| 既存の利用関連 | `usageFrequency` は自己申告の頻度です。ダッシュボードの「今日の確認」は `PATCH /api/subscriptions/{id}` で頻度・見直し日を更新するだけで、利用した日を保存していません。 |
| テスト | 専用テストディレクトリ・テスト実行スクリプトは確認できませんでした。型検査と本番ビルドを最低限の回帰確認に使い、追加する純粋関数は Node の組み込みテストで検証します。 |

## 既存データを守る実装方針

- 既存モデル・API・認証・Stripe・CSV・通知基盤を削除または置換しません。
- 日別利用を `SubscriptionUsage` の追加テーブルで保存します。`userId`、`subscriptionId`、`usedDate` の複合ユニーク制約により、同日に重複記録されないようにします。
- 利用記録APIは必ず認証済みセッションの `userId` を使い、URLの `subscriptionId` だけでは更新できないよう所有権を確認します。
- 料金、利用回数、未使用期間、候補判定などの計算は画面に埋め込まず、`src/lib` の純粋なドメインロジックへ分離します。
- 新規マイグレーションは追加方式のみとし、既存テーブルやデータを削除しません。

## 実装順序

1. 日別利用実績と集計表示
2. 1回あたりコスト
3. 健康スコアと未使用判定
4. カテゴリ重複・解約候補・年間削減可能額
5. 断捨離チャレンジ、予算、入替シミュレーション、価格履歴
6. ダッシュボード・定期確認・既存通知連携・プラン制御・モバイル最適化

各段階でマイグレーション状態、型検査、本番ビルド、既存画面への影響を確認してから次へ進みます。
